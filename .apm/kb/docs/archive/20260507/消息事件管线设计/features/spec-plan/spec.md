# 消息事件管线设计 需求说明

## 背景

旧项目中的消息处理 manager 采用单例 + 事件订阅 + 持久化 + UI 刷新混合实现，导致职责耦合高、生命周期不透明、调试成本高。  
新项目已在持久化层采用 Adapter/Schema/Store 的轻量分层，消息处理也需要保持同等架构一致性，避免把旧项目技术债复制到新项目。

## 目标

- 为 `st-virtual-file-system` 设计一套新的消息事件处理架构（非旧 manager 复制）。
- 明确事件监听、消息处理、状态更新、UI 刷新的边界与调用关系。
- 产出可审阅的 `spec + plan` 文档，作为后续编码唯一依据。

## 范围

### 包含范围

- 定义消息处理子系统的目标架构与分层职责。
- 定义与 SillyTavern 事件系统的集成方式（订阅、解绑、聊天切换处理）。
- 定义错误处理、可观测性（日志/错误上报）与测试策略。
- 定义从“旧 manager 思路”到“新架构实现”的迁移原则（仅原则，不落代码）。

### 不包含范围

- **v1（文档基线）**：仅 `spec + plan`，不进行代码实现。
- 不修改 `st-better-database` 现有实现。
- 不实现具体 SQL/DML 业务逻辑，仅定义架构承载方式。

### v2 实现阶段（当前迭代，本分支）

- **包含**：按 `plan.md` 落地**最小可运行骨架**——事件 Adapter（可 `start/stop`）、Message Controller、Message Pipeline（可为日志桩或 no-op），并与现有 `initVfsPersistenceStore` / `CHAT_CHANGED` 行为兼容（聊天切换时不长期缓存 `chatMetadata` 引用）。
- **不包含**：具体消息内容解析、SQL 执行、改写聊天文本等业务；可选 `message-runtime-store` 默认不实现。

## 功能需求

1. **事件接入能力**
   - 能接入并管理 `MESSAGE_RECEIVED`、`MESSAGE_EDITED/UPDATED`、`MESSAGE_DELETED`、`CHAT_CHANGED` 等事件。
   - 必须支持统一注册与统一解绑，避免重复订阅与泄漏。

2. **处理管线能力**
   - 事件回调只负责“调度”，业务处理放入独立 pipeline/service。
   - 必须支持消息解析、校验、转换、提交的分阶段处理。

3. **状态与持久化协同**
   - 与现有 persistence store 协同，不直接绕过 store 进行写入。
   - 聊天切换后必须触发会话级状态重载逻辑。

4. **错误处理能力**
   - 单条消息处理失败不应中断整体监听。
   - 错误必须具备可定位信息（事件类型、消息索引、失败阶段）。

5. **可测试能力**
   - 事件接线层、pipeline 层、控制器层应可独立测试。
   - 至少定义单元测试与集成测试覆盖面。

## 非功能需求

- **可维护性**：职责边界清晰，避免“大而全 manager”。
- **可扩展性**：后续新增事件类型时，最小改动接入。
- **稳定性**：遵循官方 `getContext` 与事件机制约束，不依赖不稳定内部实现。
- **可观测性**：关键流程具备调试日志与错误上下文。

## 验收标准

1. 产出 `docs/Iterations/消息事件管线设计/spec.md` 与 `plan.md`。
2. 文档明确“为什么不复制旧 manager”与“新架构分层边界”。
3. 文档包含可执行实现步骤、文件级改动点、测试用例清单。
4. 文档可直接作为下一迭代编码输入，不需额外结构性澄清。
5. **v2**：代码中存在可启停的消息事件接线；`npm run test:run` 与 `npm run build` 通过；具备针对 Adapter/Controller 的最小测试（mock `SillyTavern` / `eventSource`）。

## 风险与待确认项

- 风险 1：事件类型在不同版本 ST 中命名差异（如 `MESSAGE_EDITED` / `MESSAGE_UPDATED`）。
- 风险 2：若初始化时机不当，可能出现“事件已触发但处理器未接线”。
- 风险 3：若消息处理链无幂等保护，编辑/重试可能导致重复写入。

- 待确认项 1：第一版是否需要引入处理队列（串行化）来规避并发处理冲突。
- 待确认项 2：错误提示策略是纯日志、Toast，还是分级（用户可见/仅开发可见）。
