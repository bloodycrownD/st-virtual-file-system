# VFS 编辑器保存 / 虚拟工具时机 / 回滚 UI 优化 PRD

## 背景

1. **虚拟工具调用**：用户在聊天消息中编辑、保存含 `<virtual-tool-call>` 的内容后，预期与「新消息到达」一致应立即执行；当前表现为**保存后未执行，刷新页面后才执行**，与「编辑即生效」心智不符，且易造成重复操作或误以为未触发。
2. **编辑器保存与快照**：在 **chat 领域** 的编辑器模式下，「保存文件」与「保存快照（用于回滚）」对用户应为**同一动作**；单独「保存快照」入口增加认知负担且与真实工作流不一致。
3. **回滚 UI**：当前历史 / 快照选择与回滚区域**视觉与布局**与扩展其余界面不一致（例如字段集、原始列表、单选挤在一行等）；版本选择应进入**编辑器 header 与主操作按钮同一行**（如下拉），以节省空间并与现有工具栏模式对齐。

## 目标（含成功指标）

- **虚拟工具**：消息在 **编辑并保存** 后，若文本中存在可执行的 `<virtual-tool-call>`，应在**同一会话、无需整页刷新**的情况下完成执行（或按既有规则替换为 `<virtual-tool-result>` / 失败结果），行为与「接收消息后触发」对用户可感知层面一致。
- **保存与快照**：移除独立的「保存快照」操作；用户通过**保存**即可完成持久化，并**每次保存都**产生一条新的可回滚快照记录（仍受扩展 `snapshotMaxCount` 等既有保留策略约束）。
- **回滚 UI**：快照选择与回滚控件**符合当前扩展视觉语言**（间距、边框、色板、字号层级）；**版本（快照）选择控件位于编辑器 header 行**，与现有按钮同一行排列，小视口下可合理折行但不破坏可读性。

**成功指标（可观察）**

- 在典型 SillyTavern 流程下，**编辑保存**含虚拟工具调用的消息后，无需 F5 即可在消息文本与 VFS 状态上看到与刷新后一致的结果。
- 编辑器内**仅保留一套「保存」语义**；文档或界面中不再出现单独「保存快照」作为主路径。
- 设计走查：回滚区域无「原始拼接列表 + fieldset 单选挤行」类布局；header 行可见快照下拉与回滚相关按钮的**同一行**主布局（允许窄屏次要折行）。

## 用户与场景

- **作者 / 调试者**：在聊天里粘贴或编辑带虚拟工具调用的助手消息，保存后希望立即看到 VFS 变更与结果块。
- **日常编辑者**：在 VFS 弹窗中编辑某 chat 下文件，习惯点「保存」；期望该操作同时提供「可回滚点」，无需记两套按钮。
- **需要撤销者**：通过 header 上清晰的快照下拉选择历史点并回滚，不依赖页面底部杂乱控件。

## 范围

### 包含范围

- 修正或补齐 **消息编辑保存** 路径上虚拟工具管道触发条件，使**保存后无需刷新**即可与「接收后」行为对齐（具体事件适配属实现阶段，本 PRD 只约束**用户可验证结果**）。
- **Chat 领域、编辑器模式**：合并「保存」与「生成快照」产品语义；移除单独「保存快照」入口及相关文案。
- **快照 / 回滚 UI**：重排与样式优化；**快照选择为 header 同行控件**（推荐 `<select>` 或等价可访问组件），与保存、回滚等按钮同一 toolbar 行。
- 与既有 **FIFO 快照条数**、日志中 `snapshotId` 引用等行为兼容；不改变「快照与日志分离」的产品原则，除非本 PRD 验收需要显式说明。

### 不包含范围

- 不改变虚拟工具 **协议格式**（`<virtual-tool-call>` JSON、`last call wins`、单 `<virtual-tool-result>` 等）除非验收发现必须修正的 bug 文档化。
- 不引入「分支 / 合并」式版本管理；仍为快照回滚模型。
- 不要求改动 **执行与回滚** 全局面板（历史 Tab）的整体信息架构，除非与编辑器 header 控件重复到需产品裁定（默认本迭代以**编辑器内**为主）。

## 核心需求

1. **编辑保存即触发（与刷新等价）**：用户编辑聊天消息并保存后，虚拟工具处理逻辑应在该次保存链路内生效，**不依赖**用户手动刷新整页。
2. **保存即快照（每次）**：在 chat 编辑器模式下，每次用户触发**保存**成功，均生成一条新的快照记录（占保留额度，超出部分按既有策略淘汰）；**不**再提供与「保存」并列的单独「保存快照」主操作。
3. **回滚 UI 与布局**：回滚相关控件与当前扩展 UI 风格一致；**快照版本选择**位于编辑器 **header 与按钮同一行**（桌面优先一行；移动端允许折行但保持控件完整可点）。
4. **可访问与可读**：快照选项展示**人类可读摘要**（时间、简短说明或路径提示等），避免仅展示无分隔的长拼接串；键盘与屏幕阅读器可用（焦点顺序合理）。
5. **回归安全**：合并保存与快照后，失败路径（保存失败、快照写入失败）须有明确用户反馈，且**不应**出现「文件已保存但无对应快照」的静默分裂（若技术上偶发失败，应在验收中定义为可接受边界并提示用户）。

## 验收标准

1. **Given** 某聊天消息文本末尾含合法 `<virtual-tool-call>` 且扩展已开启虚拟工具，**When** 用户在 SillyTavern 中**仅编辑并保存**该消息（不刷新页面），**Then** 保存完成后消息内出现与既有规则一致的 `<virtual-tool-result>`（或失败结果），且 VFS 状态与刷新后一致。
2. **Given** 处于 chat 领域文件编辑器模式，**When** 查看编辑器工具栏 / header 区域，**Then** 不存在独立「保存快照」按钮或同等主入口；存在单一主「保存」语义。
3. **Given** 用户连续多次点击保存（含内容未变），**When** 每次保存均成功，**Then** 快照列表（或元数据）中快照数量按「每次一条」增加，直至受 `snapshotMaxCount` 约束发生淘汰（行为与既有 FIFO 一致）。
4. **Given** 编辑器已打开且存在至少一条快照，**When** 查看 header 行，**Then** 快照选择控件与主要操作按钮**同一行**展示（宽屏）；窄宽度下折行时仍不出现控件重叠或不可读的单选挤行问题。
5. **Given** 打开快照下拉，**When** 浏览选项标签，**Then** 每条选项为可读摘要（例如时间与类型/路径片段的组合），**不**以无结构拼接的长字符串作为唯一展示形式。
6. **Given** 选择某快照并执行回滚，**When** 操作完成，**Then** 反馈方式（toast / 状态提示）与扩展其他操作一致，且文件内容与列表刷新正确。

## 风险与待确认项

- SillyTavern 不同版本在「消息编辑保存」上可能派发不同事件名；验收需在**目标使用版本**上实测（PRD 不绑定具体事件名）。
- 「每次保存都占一条快照」在频繁保存场景下会加速 FIFO 淘汰；与产品目标一致，若后续需「节流」应另开迭代。
