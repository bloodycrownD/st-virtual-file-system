# 虚拟工作树 UI 状态机与提交回滚需求说明

## 背景

本文件聚焦“状态如何变化、提交如何记录、回滚如何生效”。目标是保证文件管理、阅读/编辑、提交记录三者在操作后保持一致。

## 目标

- 定义核心页面与对象状态机。
- 定义提交记录与回滚行为（含手动回滚记提交）。
- 定义 Tab2 批量回滚后的状态刷新规则。
- 给出异常场景下的状态一致性要求。

## 范围

### 包含范围

- 文件状态切换、删除、重命名、查看、编辑相关状态转移。
- 编辑保存、历史查询、手动回滚、批量回滚行为。
- 回滚后文件树、阅读页、编辑页一致性刷新。
- Tab2 提交记录展示与操作反馈。

### 不包含范围

- 底层存储引擎和版本控制实现细节。
- 后端接口协议字段的最终定义。
- 跨 chat 的历史合并或全局治理能力。

## 功能需求

1. **核心状态机**
   - 文件节点状态：未选中/已选中/编辑中/只读查看中。
   - 文件夹节点状态：未选中/已选中/策略配置中/幻灯片阅读中。
   - 页面状态：文件管理器/阅读页/编辑页/幻灯片模式。
   - 页面切换需记录来源，以支持返回与恢复上下文。

2. **提交记录**
   - 编辑保存生成新提交记录。
   - 提交记录至少包含：时间、操作者、操作类型、作用范围。
   - Tab2 支持按时间序浏览记录。

3. **手动回滚**
   - 用户在编辑历史中选择历史版本后可执行手动回滚。
   - 手动回滚完成后，新增一条提交记录，记录“回滚来源版本”。
   - 回滚失败时保留当前编辑内容并提示错误。

4. **批量回滚（Tab2）**
   - 用户在提交记录中选择目标记录后可执行批量回滚。
   - 回滚执行后刷新：
     - 文件管理器树与当前目录列表
     - 当前阅读页内容
     - 当前编辑页内容与历史面板
   - 刷新过程对用户有明确反馈（进行中/成功/失败），失败反馈统一走 `toastr.error` 并展示错误码。

5. **一致性与冲突处理**
   - 同一时刻同一文件仅允许一个“写入提交”生效流程。
   - 不做前置冲突拦截，回滚是否成功以执行阶段结果为准。
   - 回滚与编辑保存并发时，以后端执行结果为准返回成功/失败。
   - 回滚同样视为一次提交，成功后必须新增提交记录。

## 非功能需求

- **一致性**：操作成功后各视图最终一致；失败时给出可恢复路径。
- **可追溯性**：每次关键变更可在提交记录中追踪来源和结果。
- **可恢复性**：回滚失败不导致数据丢失，并可保留当前上下文供用户手动后续处理。

## 验收标准

1. 编辑保存后 Tab2 可看到对应新增提交记录。
2. 手动回滚后能看到新提交记录，且记录包含来源版本信息。
3. Tab2 批量回滚可执行并驱动文件管理/阅读/编辑三处一致刷新。
4. 回滚失败时 UI 不崩溃，用户能通过统一 toast 看到明确原因与错误码。
5. 不进行前置冲突校验时，执行失败可被明确感知，并可由用户后续手动处理。

## 风险与待确认项

- 并发冲突策略对用户体验影响较大，需尽早定版。

## 已确认决策（2026-05-08）

- 批量回滚不做前置冲突拦截，以执行阶段成败判定；回滚成功记为新提交。
- 错误反馈统一采用官方 `toastr` toast，展示错误码，不提供重试按钮。
- 错误码仅在 `toastr.error` 展示，格式为前置短码：`[E_<REASON>] 人类可读错误信息`。

## 错误码建议清单（回滚相关）

- `[E_ROLLBACK_FAILED] 回滚失败，请检查提交状态后重试操作`
- `[E_COMMIT_APPLY_FAILED] 提交应用失败，请稍后再试`
- `[E_HISTORY_REFRESH_FAILED] 历史刷新失败，请重新打开提交记录`

## 错误码矩阵（状态与提交相关）

- 批量回滚执行失败 -> `[E_BATCH_ROLLBACK_FAILED] 批量回滚失败`
- 单文件回滚失败 -> `[E_ROLLBACK_FAILED] 回滚失败，请检查提交状态后重试操作`
- 提交应用失败 -> `[E_COMMIT_APPLY_FAILED] 提交应用失败，请稍后再试`
- 提交历史刷新失败 -> `[E_HISTORY_REFRESH_FAILED] 历史刷新失败，请重新打开提交记录`
- 保存提交失败 -> `[E_SAVE_FAILED] 保存失败，请检查输入后重试操作`
