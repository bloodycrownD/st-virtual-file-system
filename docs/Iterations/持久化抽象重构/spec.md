# 持久化抽象重构 需求说明

## 背景

当前项目在持久化上已有过一次实践经验（参考旧项目），暴露出以下问题：

- 生命周期与上下文耦合过深（初始化时机、聊天切换时机容易错）
- 状态缓存与持久化写入耦合（隐式保存、副作用难追踪）
- `extensionSettings` 与 `chatMetadata` 访问规则不一致，导致易出错
- 缺少统一边界，后续功能扩展时容易重复造轮子

SillyTavern 官方建议已明确关键约束（尤其 `chatMetadata` 引用不能长期缓存），需要在新项目中采用更稳定、可维护的抽象方式。

## 目标

- 在 `st-virtual-file-system` 内定义一套面向 SillyTavern 的持久化抽象方案。
- 同时覆盖 `extensionSettings`（全局）与 `chatMetadata`（会话）两类存储场景。
- 通过文档输出明确“做什么/不做什么/怎么做”，作为后续实现依据。

## 范围

### 迭代上下文版本

- **v1（设计期）**：仅产出 `spec.md` 与 `plan.md`，不做代码落地。
- **v2（实现期，当前分支）**：基于已确认的 `spec.md`/`plan.md` 执行实现与测试补齐。

### 包含范围

- 定义持久化分层职责与边界（Adapter / Schema / Store）。
- 定义 `extensionSettings` 与 `chatMetadata` 的访问与写入规范。
- 定义聊天切换（`CHAT_CHANGED`）下的状态重载策略。
- 定义最小可落地实现范围（后续迭代实现时参考）。

### 不包含范围

- v1 设计期不进行代码实现与重构落地。
- 不修改 `st-better-database` 的现有持久化实现。
- 不包含完整业务功能开发（仅针对持久化架构层）。

## 功能需求

1. 必须支持扩展级配置持久化（`extensionSettings`）：
   - 提供读取、默认值回填、写入、保存触发（`saveSettingsDebounced`）能力。
2. 必须支持会话级配置持久化（`chatMetadata`）：
   - 提供读取、默认值回填、写入、保存触发（`saveMetadata`）能力。
   - 明确禁止长期缓存 `chatMetadata` 引用，必须按官方方式按需读取。
3. 必须定义统一的状态模型与序列化边界：
   - 存储内容必须为 JSON 可序列化数据。
   - 复杂对象需通过 codec/schema 显式转换。
4. 必须定义聊天切换策略：
   - 监听 `CHAT_CHANGED`，触发 chat 级数据重载。
   - 重载行为与 UI 状态同步机制需可预期。
5. 必须定义错误处理策略：
   - 数据缺失、字段不兼容、反序列化失败时可回退默认值并不中断主流程。

## 非功能需求

- **稳定性**：遵循官方 API 约束，不依赖 SillyTavern 内部非稳定模块导入。
- **可维护性**：职责清晰，避免“超大 manager”集中承载全部逻辑。
- **可测试性**：Adapter/Schema/Store 可分层测试，便于单测与回归验证。
- **可扩展性**：后续新增配置项不应影响既有持久化流程与调用方式。

## 验收标准

1. 产出 `spec.md` 与 `plan.md`，并覆盖目标、范围、约束、风险与实施路径。
2. 文档中明确：
   - 为什么旧模式容易出错；
   - 新抽象如何避免典型问题（引用失效、时序、隐式副作用）。
3. 文档中存在可直接执行的实现步骤与测试策略（供下一迭代编码使用）。

## 风险与待确认项

- 风险 1：后续实现时若继续保留隐式自动保存（如 Proxy 拦截），复杂度会反弹。
- 风险 2：若 UI 状态与持久化状态同步策略不统一，聊天切换后可能出现视觉“回跳”。
- 待确认 1：第一版实现是否引入版本化迁移（schema version + migrate）。
- 待确认 2：复杂对象（如未来 VFS 树/索引）是否统一采用 codec 进行显式序列化。
